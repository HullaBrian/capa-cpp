# Parity notes

This is the edge-case knowledge buried in capa's source that a port has to keep: the
behaviors that look accidental but decide what the output is. These are the ones capa-cpp had
to reproduce on purpose, where they live, and how each is checked. "capa" means the Python
reference implementation (9.4.0 at the time of writing).

## Rules

| capa behavior | where in capa-cpp | checked by |
|---|---|---|
| Rules are read with PyYAML, which types plain scalars by YAML 1.1: `number: 010` is 8, `0x10` is 16, `1_000` and `12:30` are ints, `yes`/`on` are booleans; quoted values stay strings. `string: 123` is therefore an invalid rule, and `count(...): 2` is an int, not a string. | `rules.cpp`: `yval`, `resolve_yaml_int` | unit tests |
| `parse_int` is Python's `int(s, 16)` for `0x`/`-0x` prefixes and `int(s, 10)` otherwise: whitespace is stripped, underscores are allowed, `0X10` is invalid. | `rules.cpp`: `python_int`, `parse_int` | unit tests |
| Inline descriptions (`value = description`) split at the first ` = ` for every feature **except** `string` (so `substring: foo = bar` is "foo"). Only one description per feature. | `rules.cpp`: `parse_description` | unit tests |
| `os:`/`arch:`/`format:` values are validated before the description is split, so `os: windows = x` is invalid. `format:` only accepts pe/elf/dotnet. | `rules.cpp`: `build_feature` | unit tests |
| Features are validated against the rule's scopes (`SUPPORTED_FEATURES`); `Substring`/`Regex` count as `String`. | `rules.cpp`: `ensure_feature_valid_for_scopes` | unit tests |
| Duplicate features in one statement are dropped (first kept, with its description); statements are never deduplicated (capa compares them by identity). | `rules.cpp`: `build_unique` | unit tests |
| `com/class` / `com/interface` expand to an `or:` of every registered GUID, as a string and as bytes; the feature's own description is dropped. | `rules.cpp`: `translate_com_feature`, `com_database.cpp` (generated by `scripts/gen_com_database.py`) | unit tests |
| The query optimizer (`capa/optimizer.py`) stably sorts `and`/`or`/`some` children by cost (os/arch/format 0, hash lookups 1, substring/regex/bytes 2, statements 1 + children) after subscope extraction. The order is visible: it is the child order in every match tree. | `rules.cpp`: `optimize_node` | unit tests, parity |
| The feature index is built in capa's scope order (dynamic scopes, then static) with one shared score table, and among an `and`'s children the highest score wins, then the fewest features, then the first. | `rules.cpp`: `RuleSet::RuleSet`, `index_rec` | paranoid matcher fixtures |
| Only `.yml` files are rules, and nothing under a path containing `.git`. | `rules.cpp`: `collect_rule_file_paths` | rule counts equal capa's |
| capa names extracted subscope rules `<parent>/<uuid4>`; capa-cpp uses `<parent>/subscope-<n>`. The name is never part of a successful match (see splicing below). | `rules.cpp`: `extract_subscopes_rec` | `compare_results.py` normalizes it |

## Matching

| capa behavior | where | checked by |
|---|---|---|
| `Some` short-circuits only after evaluating a child, so an empty `optional:` is false in the short-circuit pass that decides whether a rule matched. | `engine.cpp` | unit tests |
| Regexes are Python's, always with `re.DOTALL`; `$` also matches before a final newline. | `pyregex.cpp` | unit tests |
| `bytes:` and `os:` stop at the *first* qualifying feature in the scope's (insertion-ordered) feature set and report only its locations. capa-cpp picks the one seen earliest in the walk, i.e. with the lowest location. | `engine.cpp`: `first_seen` | parity |
| Numbers are unbounded Python ints: `0xFFFFFFFFFFFFFFFF` and `-1` are different features. Backends that read machine words (IDA's `mask_op_val`, viv-style masked immediates, sandbox arguments) produce unsigned values. | `feature.h`: `Feature::big` | parity (x64 and CAPE inputs carry values ≥ 2^63) |
| The span-of-calls matcher suppresses a rule matched in the immediately preceding span unless a newly matched rule depends on it. | `capabilities.cpp` | matcher fixtures (`dynamic/span.yml`) |
| File scope merges in the lower scopes' match features; features without an address are present with an empty location set. | `static_caps.cpp`, `capabilities.cpp` | parity |

## Result document

| capa behavior | where | checked by |
|---|---|---|
| Written with `model_dump_json(exclude_none=True)`: pydantic *field* names (`import_`, `class_`, `function_name`, `operand_number`, `is_subscope_rule`, `malware_category`, `base_address`), and no member whose value is None — so `namespace` is absent when unset, `scopes` omits the unsupported flavor, a NO_ADDRESS address has no `value`, and `argv` is absent when empty. | `render.cpp`, `freeze.cpp` | capa's own pydantic model loads every document; parity |
| A successful `match:` node has the matched rule's (or, for a namespace, every matching rule's) trees spliced in as children, at the locations it matched; a call address with no exact match takes the most recent match at or before it in the same thread. A `match:` of a subscope rule becomes a `subscope` statement node. | `render.cpp`: `MatchWriter` | parity |
| att&ck / mbc specs are parsed by `parse_parts_id`: the id is whatever follows the last space of the last part, brackets stripped. | `render.cpp`: `parse_spec` | parity |
| The static layout lists, per function in extractor order, the basic blocks any basic-block-scoped rule matched at (subscope rules included); the dynamic layout lists every call that appears in *any* location of any match tree. | `result_document.cpp` | parity |
| `meta.analysis.format` falls back to the input format (`freeze` for a freeze file) when the extractor has no format feature. | `result_document.cpp` | — |

## Known differences

- capa's integer-like addresses (absolute, relative, file offset, .NET token) are `int`
  subclasses and so compare equal across kinds; capa-cpp keeps them distinct. This could only
  show for a location set holding two kinds with the same value, which no backend produces.
- `number: 1` and `number: 1.0` are one feature in capa (Python's `1 == 1.0`) and two in
  capa-cpp. No rule or backend produces a float number today.
- Regex constructs with no ECMAScript equivalent (lookbehind, atomic groups, possessive
  quantifiers, scoped inline flags) do not compile; the rule loads but the regex never matches,
  and the loader says so. capa-rules has none.
- capa refuses to run when any rule is invalid or a dependency is missing; capa-cpp skips the
  rule and says so (it predates full rule support, and an embedding host should not fail on one
  bad private rule). With capa-rules nothing is skipped.

## IDA backend extensions

capa's IDA backend raises on a file type other than PE, ELF or raw binary, so it has no output
for a database opened on a process minidump. capa-cpp's IDA backend accepts one, and for that
input only:

- emits `os: windows` (`capa-cpp/src/ida/global_.cpp`), since IDA's file type name has no "PE"
  in it;
- resolves `api:` through the dump's export and import tables (`capa-cpp/src/ida/insn.cpp`);
- in the plugin, skips functions in Windows system modules unless asked not to
  (`capa-cpp/src/ida/extractor.cpp`). `IdaExtractor` defaults to scanning everything, and
  `capa-idalib` always does.

Whether the input is a dump is decided from the input file, not from IDA's loader name. A PE or
ELF database is extracted exactly as capa's IDA backend extracts it, whatever the plugin's
settings.
